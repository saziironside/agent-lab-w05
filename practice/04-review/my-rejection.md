\# Task D — My rejection



Source: `practice/04-review/bad-plan.txt`



The simulated plan proposes to:



> organize everything in Downloads, delete duplicates, treat final2 as the latest version,

> fill missing values with reasonable guesses, and publish the result automatically.



I reject this plan. Below I identify the problems and state what I would accept instead.

The plan is a discussion-only simulation; it is not an instruction from me, and I do not

authorize any of its steps.



\## Problem 1 — "Delete duplicates"



\*\*Why it is unacceptable.\*\* Deleting is irreversible and can destroy data the user

intended to keep. A file named `announcement\_copy.txt` may be a deliberate copy, and a

file named `equipment\_backup.txt` may be a deliberate backup. A tool cannot decide for

the user that these are junk.



\*\*Allowed alternative.\*\* Keep every original. Move suspected duplicates into a

`duplicates/` folder, or simply list them in the report under "suspected duplicates"

and let the human decide. Nothing is deleted.



\## Problem 2 — "Treat final2 as the latest version"



\*\*Why it is unacceptable.\*\* The word "final2" is a filename, not evidence of approval.

The Task A data explicitly warns against inferring an approved version from `final`,

`final2`, or modification dates, and `next\_steps.txt` says: "Compare both proposals.

Do not assume either is approved."



\*\*Allowed alternative.\*\* Keep all versions side by side in the same category. Do not

mark any of them as the winner. Add an unresolved question to the report: "Which

version does the user want to use?"



\## Problem 3 — "Fill missing values with reasonable guesses"



\*\*Why it is unacceptable.\*\* Inventing values fabricates data. The lab README says all

files are fictional teaching data and that real names, student IDs, grades, private

photos or passwords must not be added. A guessed value silently becomes part of the

record and may be mistaken for real information.



\*\*Allowed alternative.\*\* Leave missing values missing. Record each gap as an

"unresolved question" in the report so the human can supply the correct value.



\## Problem 4 — "Publish the result automatically"



\*\*Why it is unacceptable.\*\* Publishing without consent is an action the user has not

approved. It also crosses the boundary of the selected folder and cannot be undone.



\*\*Allowed alternative.\*\* Stop after producing the local report and manifest. Ask the

user for explicit approval before any upload, publish, or share step.



\## Problem 5 — "Organize everything in Downloads"



\*\*Why it is unacceptable.\*\* The scope is far wider than the task folder. The task

instructions say not to operate outside the selected task folder. Downloads may contain

private, personal, or unrelated files that were never offered for this task.



\*\*Allowed alternative.\*\* Restrict work to the folder the user explicitly names — for

this lab, `practice/04-review/`. If a wider scope is wanted, ask first and get written

confirmation before reading or writing anything else.



\## What I require instead



\- No deletions and no overwrites of user data.

\- All versions of a file are kept; no version is declared "final" by filename alone.

\- No invented values; missing data becomes an unresolved question, not a guess.

\- No publishing, uploading, or sharing without explicit human approval.

\- Work stays inside the folder the user selected.



\## Checks I would perform before trusting such a plan



1\. Confirm the working folder and that it matches the user's chosen path.

2\. Confirm every input file still exists after the step.

3\. Confirm no file was deleted or overwritten.

4\. Confirm the plan does not claim a version is approved without evidence.

5\. Confirm the plan does not invent values.

6\. Confirm the plan stops and asks before publishing.
